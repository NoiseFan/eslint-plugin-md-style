# Repository Guidelines

## Workspace Layout

This repository is a pnpm workspace (`packages/*`) containing two TypeScript ESM packages:

- `packages/eslint-plugin-md-style/`: the published ESLint plugin. `index.ts` is the public entry point; `rules/` contains rule implementations; `parser/`, `utils/`, and `types/` contain shared internals; `scripts/` contains generation and release tooling.
- `packages/ast/`: the private `@md-style/ast` package. Its source entry is `src/index.ts`.
- `packages/eslint-plugin-md-style/tests/fixtures/input/` and `output/`: integration fixture pairs. `tests/_fixtures/` is generated while tests run and must not be edited as source.
- Root files such as `eslint.config.ts`, `tsconfig.json`, `vitest.config.ts`, and `pnpm-workspace.yaml` configure the whole workspace.

Generated output should not be committed. `packages/eslint-plugin-md-style/types/typegen.d.ts` is generated by `gen:types`. The root `README.md` is the canonical README; `pnpm gen:rules` refreshes its rule table and synchronizes the package README.

## Commands

Run commands from the repository root with Node `>=20.19.0` and the pnpm version declared in `package.json`.

- `pnpm install`: install workspace dependencies and configure git hooks.
- `pnpm lint` / `pnpm lint:fix`: check or fix the entire workspace.
- `pnpm test --run`: run all Vitest projects once. Use `pnpm test` for watch mode.
- `pnpm test:cov --run`: run the full suite with V8 coverage.
- `pnpm --filter eslint-plugin-md-style test --run`: test only the plugin package.
- `pnpm --filter eslint-plugin-md-style typecheck`: type-check the plugin package.
- `pnpm --filter eslint-plugin-md-style build`: generate rule typings and bundle the plugin.
- `pnpm --filter @md-style/ast typecheck` / `build`: validate or bundle the AST package.
- `pnpm gen:rules`: regenerate the README rule table after rule metadata or registration changes.

## Code and Rule Conventions

Follow the repository's `@antfu/eslint-config` style: no semicolons, single quotes, and concise typed exports. Use `@/` for plugin-package imports and `@tests/` for test helpers. Do not use `src/...` imports. Rule modules must not import other rule modules directly; move reusable logic into `rules/shared/`, `parser/`, or `utils/`.

Keep rule directories kebab-cased. A rule normally exports `RULE_NAME`, stable message IDs, metadata, and its implementation from `rules/<rule-name>/index.ts`, with colocated `*.test.ts` files. Register new rules in `rules/index.ts`. Treat fixer behavior as public behavior: fixes must be safe and idempotent, and rule metadata must accurately state whether the rule is recommended or fixable.

## Testing and Documentation

Use `eslint-vitest-rule-tester` for rule-level valid/invalid cases, including exact diagnostics and fixed output. Keep parser, analyzer, and utility tests next to their implementations. Add fixture input/output pairs when behavior needs end-to-end coverage across the complete plugin config. Update snapshots only when the behavior change is intentional.

For every rule change, cover edge cases and autofix idempotence where relevant, then update the README examples or rule table if user-visible behavior changed. Before handing off a change, run the narrowest relevant tests plus `pnpm lint` and the affected package's `typecheck`; run the full suite for parser, shared fixer, or configuration changes.

## Commits and Pull Requests

Use Conventional Commits with an optional useful scope, such as `fix(valid-heading-anchor): ...`, `feat(parser): ...`, or `chore: ...`. Keep subjects imperative. Pull requests should explain the user-visible effect, name affected rules/packages, link related issues, and include before/after Markdown for fixer changes.
